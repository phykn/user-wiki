Shared execution guidance after [[intuition]].

Ask only when the answer changes the next action, implementation, claim, or risk. If available evidence decides the route, proceed.

## Authority

Match actions to the request:

- Question, explanation, review, diagnosis, or status: inspect and answer. Do not edit or fix unless the user also asks for a change.
- Build or change: edit the requested local workspace and verify the changed surface.
- Commit, push, deploy, publish, send, delete, credential change, or external durable write: act only when the user explicitly includes it or requests an outcome whose agreed delivery route requires it.
- Durable preference update: follow [[policy]].

Before a destructive or external action, confirm that the target and effect are within the requested route. If that route fails, try to restore it; report the concrete blocker before choosing a materially different route.

Preserve pre-existing and unrelated working-tree changes. Stage only files that belong to the request. Do not inspect unrelated sibling workspaces merely because they are available.

Do not read secret values unless the requested operation requires them. Never reproduce secrets in tool output or the final report.

Read every applicable instruction file from the target root to each path in scope, resolving the chain separately for each affected subtree. Within the same authority, a more specific nested rule controls only its scope.

## Work Loop

For work with a local change or more than one proof target:

1. Name the requested outcome and what would make it a different task.
2. Read the applicable local instruction chains and the smallest reliable evidence.
3. Make the smallest coherent change that resolves the protected failure.
4. Verify with evidence matched to the changed surface.
5. Check whether a confirmed durable update was explicitly requested.

Expand scope when the same user path, reader understanding, claim, command, test, or local invariant would otherwise remain wrong. Split work when it needs a new deliverable, behavior contract, source set, external action, or user decision.

Do not turn planning, critique, or tool use into a separate ritual when the artifact, action, and proof are already clear.

## Evidence

Prefer commands run, reproduced behavior, rendered output, checked sources, inspected diffs, or direct rereading. If execution is unavailable, state what static reasoning proves and what remains uncertain.

Choose commands from the applicable instruction chains, README, manifest, or existing tests. Label inferred commands and static-only checks. A narrow passing check does not prove a broader outcome.

For work with several meaningful surfaces, keep each surface independently checkable. Before reporting completion, compare the result with the original request and later corrections.

## Text Edits

Apply obvious spelling, spacing, mechanical count, and formatting fixes directly. Ask before changing ambiguous meaning, claim strength, or technical interpretation.

Preserve accepted content during formatting-only work. When the reader would retain the same wrong understanding or next action, the defect is still in scope.

## Continuity

After interruption, compaction, or correction, recover the latest request, original goal, current scope, constraints, and proof target before acting. Follow the latest user steering when it conflicts with an older interpretation.

Keep a broad goal open unless evidence covers every explicit requirement. Report a verified milestone as a milestone, not as completion of the larger goal.

## Report

For work that changed a maintained surface, report:

1. What user path or problem was protected.
2. What changed or was concluded.
3. What evidence was checked.
4. Relevant unverified or out-of-scope work.
5. Whether durable guidance changed or remains only a proposal.
